# Sandbox Isolation Security Audit

Security analysis of the krun-backed microVM isolation layer in
`nimbus-sandbox`, including the patched `crun` runtime and the OCI bundle
configuration generated by the krun backend.

## Scope

- OCI bundle generation (`crates/nimbus-sandbox/src/backends/krun/bundle.rs`)
- Patched crun with TSI port-map annotation support
- Host-side process privileges and namespace configuration
- Guest-side user switching via `nimbus-guest-user-switch`
- Buildah image mount trust boundary

This audit is the krun/microVM layer review. Production tenant isolation is
broader and is recorded in the completed baseline at
`docs/plans/archive/tenant-isolation-control-plane-plan.md`, which covers V8
isolate security posture, the `nimbus-runtime` HostBridge trait surface,
application-layer tenant authorization, sandbox filesystem state, volumes,
image admission, secrets, quotas, and cross-layer cleanup.
The current enterprise tenant-isolation posture is published at
`docs/tenant-isolation.md`.

Out of scope for the krun patch findings below: proving that those broader
tenant-isolation controls are complete. A closed microVM finding must not be
read as a production multi-tenant isolation claim by itself.

## Architecture Context

The krun sandbox launch chain:

```
buildah unshare -> conmon -> /usr/libexec/nimbus/crun (patched) -> libkrun -> KVM microVM
```

Each service sandbox gets its own hardware-isolated microVM running a real
Linux kernel (`libkrunfw` 5.3.0). The primary security boundary is KVM
hardware isolation, not OCI namespace/cgroup confinement alone.

TSI (Transparent Socket Impersonation) intercepts `AF_INET` syscalls inside
the guest kernel and maps guest ports to host ports, removing the need for a
network namespace or virtual NIC.

## What Is Sound

### Hardware isolation via KVM

Each service runs in its own microVM with its own kernel. A guest-side
compromise does not escape the VM boundary — the attack surface is the KVM
hypervisor and virtio device model, which is significantly smaller than a
container namespace boundary.

### Localized patch surface

The crun patch is localized to `src/libcrun/handlers/krun.c`. It reads one
OCI annotation (`krun.port_map`), validates the annotation before side
effects, and calls either legacy `krun_set_port_map()` for
`HOST_PORT:GUEST_PORT` entries or a bind-address-capable libkrun hook for
address-bearing entries. No new syscall paths or IPC channels are added.

### Validated OCI bundle generation

The Rust bundle builder validates:

- Port binding uniqueness (no duplicate names, no duplicate host ports)
- Non-empty process args
- Terminal mode disabled (service-mode only)
- Resource limit coherence (cpu_count requires memory_limit_bytes)
- Minimum memory floor (1 MiB)

### Guest user separation

The VMM process runs as root on the host (required for `/dev/kvm`), but
inside the guest, `nimbus-guest-user-switch` drops privileges to the image's
declared `USER` before starting the service process. The helper binary is
bind-mounted read-only at `/.nimbus/nimbus-guest-user-switch`.

## Findings

### F1: Explicit seccomp profile in OCI spec

**Severity: Medium | Likelihood: Low | Status: Closed on Linux smoke**

The generated krun `config.json` now includes a `linux.seccomp` section with
`SCMP_ACT_ERRNO` default denial and an explicit krun/libkrun syscall
allowlist.

Linux proof on Debian 13 `minicloud` showed the allowlist is active and still
boots an image-backed BusyBox service. The proof also exposed real libkrun
rootfs I/O needs, so the allowlist now includes `close_range`, vectored I/O
syscalls such as `preadv`, and read-only xattr syscalls such as `fgetxattr`.

### F2: Explicit capability dropping

**Severity: Medium | Likelihood: Low | Status: Closed on Linux smoke**

The OCI spec now sets explicit `process.capabilities` lists for the host-side
krun VMM process instead of inheriting all root capabilities. The current
minimum set is:

- `CAP_NET_ADMIN`
- `CAP_NET_BIND_SERVICE`
- `CAP_SYS_ADMIN`

Linux smoke proved this set is sufficient for the patched crun/libkrun launch
path while dropping the rest of the inherited root capability surface.

### F3: `noNewPrivileges` flag

**Severity: Low | Likelihood: Low | Status: Closed on Linux smoke**

The OCI spec now sets `process.noNewPrivileges: true`. Linux smoke proved
this does not break krun/libkrun VM launch, and it prevents host-side
privilege escalation via setuid/setgid binaries or file capabilities during
the crun/libkrun setup window.

### F4: TSI ports bind only to the configured host address

**Severity: Medium | Likelihood: Medium | Status: Closed on patched stack**

The krun bundle intentionally omits the network namespace so TSI port
mappings work; TSI-bound ports appear in the host network namespace. Nimbus
therefore must carry the configured `SandboxPortBinding::host_address` all
the way into the libkrun listener bind call.

This path is now implemented and fail-closed:

- Nimbus formats `krun.port_map` as `ADDR:HOST_PORT:GUEST_PORT`, with IPv6
  rendered as `[ADDR]:HOST_PORT:GUEST_PORT`.
- patched `nimbus-crun` validates legacy and address-bearing annotations and
  rejects malformed, out-of-range, duplicate, empty, or too-long input before
  any libkrun call.
- address-bearing entries require libkrun to export
  `krun_set_port_map_with_bind_address`; otherwise `nimbus-crun` fails launch
  instead of silently widening exposure.
- `nimbus/nimbus-libkrun` release `v1.17.4-nimbus.1` implements
  `krun_set_port_map_with_bind_address()` and binds TSI listeners to the
  requested host address. Nimbus installs it as a private runtime stack under
  `/usr/libexec/nimbus/lib`.

Linux proof on `minicloud` rendered
`krun.port_map = "127.0.0.1:18081:8081"` and ran the image-backed smoke with
`NIMBUS_KRUN_SMOKE_NON_LOOPBACK_HOST=192.168.4.29`. The VM answered localhost
readiness and refused `192.168.4.29:18081`, proving the host bind remained
loopback-only on the patched stack.

### F5: Root VMM process lifetime

**Severity: Low | Likelihood: Low**

The crun process runs as root for the entire VM lifetime, not just during
`/dev/kvm` initialization. This is required by the current krun architecture
but expands the window during which a host-side crun/libkrun vulnerability
could be exploited with root privileges.

**Recommendation:**

- Prefer udev rules granting `/dev/kvm` access to a dedicated `kvm` group
  rather than running as root, if libkrun supports non-root operation.
- If root is truly required, investigate whether crun can drop privileges
  after KVM initialization via the OCI lifecycle hooks.

### F6: Buildah image mount trust boundary

**Severity: Medium | Likelihood: Low**

`buildah unshare` creates a user namespace and mounts the OCI image's rootfs
overlay. The `conmon` + `crun create` command runs inside this unshare
session. The rootfs overlay is traversed on the host before the VM boots.

A malicious OCI image layer could attempt host-side path traversal via
symlinks or specially crafted overlay whiteouts during the mount phase. This
is mitigated by buildah's existing symlink protection, but the trust boundary
is worth noting because image content is tenant-controlled.

**Recommendation:**

- Pin images to digest references (`image@sha256:...`) rather than tags for
  production deployments.
- Verify image provenance (signatures, attestations) before allowing
  buildah mount.
- Monitor for upstream buildah CVEs related to overlay/mount handling.

### F7: Annotation parsing in patched crun (C code)

**Severity: Low | Likelihood: Low | Status: Closed with parser harness**

The `krun.port_map` annotation is parsed with C string splitting in the
patched `handlers/krun.c`. The parser now accepts legacy
`HOST_PORT:GUEST_PORT`, IPv4 `ADDR:HOST_PORT:GUEST_PORT`, and bracketed IPv6
`[ADDR]:HOST_PORT:GUEST_PORT` entries.

The parser rejects these cases before any libkrun port-map call:

- Integer overflow on port number conversion (e.g., `"999999:8080"`)
- Missing null-termination edge cases
- Behavior on malformed input (e.g., `":::,"`, empty string, very long
  strings)
- Duplicate host bind-address/port pairs

Targeted coverage lives in `nimbus-crun/tests/port_map_parser_test.c` and is
run through `scripts/verify-port-map-parser.sh` and
`scripts/verify-patch.sh`.

### Production Exposure Gates

Before Nimbus claims production-safe multi-tenant microVM service exposure:

- `docs/plans/archive/tenant-isolation-control-plane-plan.md` closed the
  cross-layer tenant isolation gates for compute, networking, storage,
  HostBridge/runtime grants, volumes, images, secrets, quotas, and cleanup.
- F6 must have a production image-admission policy for tenant-controlled
  images.
- The production runtime package must pin and ship the patched crun/libkrun
  stack validated here, or rerun the same localhost-only smoke for any
  replacement stack before exposure is claimed.
- F1, F2, F3, F4, and F7 are closed for the patched Linux krun stack recorded
  by `docs/plans/archive/sandbox-microvm-hardening-plan.md`.
- F5 may remain an accepted residual risk only if it is documented for
  operators and tied to the KVM/libkrun threat model.
- F7 must stay green in the patched crun verification lane.

Implementation order:

1. `docs/plans/archive/tenant-isolation-control-plane-plan.md` as the
   completed cross-layer production tenant-isolation control-plane baseline.
2. F6 as distribution/deploy policy before tenant-controlled production
   images.
3. Keep runtime packaging pinned to the published `nimbus-crun` /
   `nimbus-libkrun` pair.
4. F5 non-root/root-lifetime investigation as residual-risk hardening.

### Tenant Isolation Boundary Notes

The following statements are invariants for production tenant isolation and
are routed to `docs/plans/archive/tenant-isolation-control-plane-plan.md`
rather than the krun patch audit:

- OCI bundle generation must consume an admitted tenant-scoped sandbox spec;
  tenant-controlled paths, mounts, devices, capabilities, and annotations must
  not flow directly into `config.json`.
- Mutable sandbox artifacts must be tenant-owned: bundle directory,
  materialized rootfs, logs, manifests, state, named volumes, port leases, and
  cleanup markers.
- Shared immutable caches are allowed only when content-addressed and verified
  before use; they must not become shared writable tenant state.
- Loopback service publication is the default. Public or LAN exposure is an
  explicit operator policy decision, not a Compose default.
- Runtime `service` grants and network grants are separate. A tenant runtime
  must not be able to bypass `ctx.services` by scanning localhost ports unless
  the network grant explicitly admits the same tenant-owned endpoint.
- HostBridge operations must use the server-owned invocation tenant. Tenant ID
  must not be accepted from JavaScript payloads.
- Native HTTP/API entrypoints must bind a verified principal/session to the
  path tenant before calling storage or service lifecycle operations.

## Overall Assessment

The primary security boundary — KVM hardware isolation — is solid. None of
the findings above represent a critical vulnerability today. They are
hardening gaps that become increasingly relevant as the project moves toward
multi-tenant production deployment.

The patched crun remains a single-annotation design with a localized parser.
The parser now has targeted malformed-input coverage, and address-bearing
entries fail closed unless the paired libkrun bind-address hook is available.
On the validated Debian 13 proof stack, the hook exists and the Linux smoke
proves localhost-only TSI exposure.

Priority order for remediation:

1. **F6** (image trust) — operational policy, not a code change
2. **Patched stack packaging** — keep shipping the validated
   `nimbus-crun`/`nimbus-libkrun` pair
3. **F5** (root lifetime) — accepted residual for v1 with tracking
