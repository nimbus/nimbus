# FU10 — projection reconciliation liveness flake

Status: fixed. The flake is a product defect and the fix is a product change in
`nimbus-engine`; no assertion in the flaking test itself was changed. The fix
then destabilised one neighbouring test, which is diagnosed and corrected here
too.

## Symptom

`crates/nimbus-system/src/projection/reconciliation_tests.rs`, the shared
`wait_for_row_count` helper:

```
runtime reconciliation should publish without another source mutation: Elapsed(());
source_snapshot=Ok(([TableName("tasks")], ProjectionToken { ... durable_sequence: SequenceNumber(1) }));
diagnostics=Ok(MutationJournalStats { ... });
visible_row=None
```

The 10s wait expires with no projected row while every frontier on the source
tenant reports caught up (`assignment_lag: 0, apply_lag: 0, publication_lag: 0,
visibility_lag: 0`), no dirty scopes, no delayed retries, and no consecutive
failures. `ci-pr` runs `retries = 0`, so a single occurrence fails the whole
MySQL provider lane.

`fu1.md` attributed this as pre-existing via interleaved same-binary ABBA and
hypothesised "a liveness race in the projection observer's post-restart
reconciliation, entirely inside nimbus-system". The race is real but it is not
in nimbus-system, and it is not a wedge.

## What the diagnostics were hiding

Three facts sent the investigation the wrong way and are worth recording:

- The panic line quoted in `fu1.md` is inside `wait_for_row_count`, which is
  shared by three call sites in the file. Failures attributed to
  `assert_provider_restart_reconciles_scope` also come from
  `prepare_two_engine_projection_contract`, on a different tenant. Run duration
  and `source_snapshot.durable_sequence` discriminate them.
- `observer_spawned_work_depth` sat at 1-2 with `dirty_scope_count: 0` and
  `delayed_retry_count: 0`. That reads as "work registered and parked", which
  looks like a lost wakeup. It is really "work registered and running slowly".
- `committer_inbox_depth` reads 0 while a caller is blocked, because the
  committer actor has already dequeued the message and is awaiting the ordered
  publisher. Every queue-depth counter therefore reports idle during the stall.

The system tenant's own `committer_lease_last_success_age_millis` was the only
counter that told the truth: `Some(9050)` and `Some(4900)` in failing runs,
i.e. the `_nimbus` renewal worker had made no progress for most of the window.

## Root cause

Instrumented the projection path with timestamped probes at each stage
(`nimbus-system` projection task and record path, `nimbus-engine` count/wait,
committer actor, ordered publisher). A failing run, times in ms:

```
852325  task-entry     tenant=projection-mysql-restart-... gen=1
852433  task-lock
852499  record-begin   table=tasks
852606  stage=ensure-system
852901  ensure-system schema-begin index=0
   ...  19 x (actor send-opaque -> publisher opaque-job-begin/end -> drained)
861717  ensure-system schema-begin index=15
862391  PANIC (10s wait expired)
```

`record_table_state_for_generation_async` begins with
`ensure_system_tenant_async`, which unconditionally re-declares every system
table schema plus the projection fence schema — 19 `set_table_schema_async`
calls — on the shared `_nimbus` tenant, while holding the per-tenant
`projection_lock`. Against MySQL each costs ~500-700ms end to end, so the fixed
setup cost of a projection is ~10s and the wait times out at index 15 of 18,
before the projection reaches its actual work.

None of those 19 writes changes anything. `apply_set_table_schema`
(`crates/nimbus-engine/src/engine/schema.rs`) had no idempotence check: it
persisted the schema and advanced the journal even when the incoming schema was
identical to the stored one. In a failing run the `_nimbus` journal reached
sequence 39 for two projections — 37 of those records were no-ops.

So the defect is write amplification on the critical path, not a wedge. The
work always completes; the probes show `opaque-job-end` and `record-end` landing
*after* the panic. It is a product liveness defect: the projection's fixed cost
scales with the number of system tables and with per-commit provider latency,
and nothing bounds it.

## Fix

`crates/nimbus-engine/src/engine/schema.rs`: `set_table_schema` and
`set_table_schema_async` answer a redeclaration of the stored schema from the
in-memory snapshot instead of routing it through the committer.

`stored_table_schema_matches` reconciles index metadata against the stored table
schema exactly as the commit path does, then compares. On a match,
`finish_unchanged_table_schema` still checks tenant admission
(`enter_operation`) and committer-lease ownership
(`ensure_committer_lease_for_assignment`), so a caller that has lost the tenant
sees the same error the committer path would have raised, and then returns. No
durable record is appended and no schema-change observer is notified — with no
schema change there is nothing to re-project.

This mirrors the existing precedent in the same file:
`apply_loaded_schema_snapshot` already returns early when the loaded schema
equals the current one.

Regression test: `tests::engine_skips_the_durable_write_for_an_unchanged_table_schema`
in `crates/nimbus-engine/src/tests.rs` asserts the durable head advances by
exactly one for a new schema, does not move across five redeclarations, still
advances by one for a changed schema, and that the stored schema is correct
after each phase.

Also kept: `wait_for_row_count` now dumps the system tenant's mutation-journal
diagnostics alongside the source tenant's. That is what made the `_nimbus`
stall visible; without it the failure looks like a source-tenant problem.

## Evidence

Local MySQL fixture (`scripts/external-provider-fixture.sh`), macOS, debug
build.

Read the rates with one caveat in mind, because it dominates them: **every
failed run leaks its MySQL databases.** Fixture cleanup runs at the end of the
test body, so it is skipped on failure. Across the investigation the fixture
grew from 53 schemas / 856 tables to 155 / 2009, per-commit latency rose with
it, and the isolated base failure rate rose from ~1/12 to 19/20. Rates are only
comparable when they were measured at the same fixture state.

Pollution-matched pairs, measured back to back at ~155 schemas / 2009 tables:

| scope | build | runs | FU10 failures |
| --- | --- | --- | --- |
| target test, isolated | base | 20 | 19 |
| target test, isolated | fix | 30 | 0 |
| full lane, `--test-threads=4` | base | 5 | 3 |
| full lane, `--test-threads=4` | fix | 15 | 0 |

On a **clean** fixture the base flake did not reproduce: a second base batch ran
15 lanes as the fixture drained back to empty and saw 0 FU10 failures in the 14
lanes that completed (the 15th is the cleanup hang described below).

That is the expected shape, and it is why the fix is a liveness fix rather than
a correctness one. The mechanism is a fixed setup cost of 19 no-op commits at
~500-700ms each, which lands at roughly the 10s wait budget. On a clean fixture
it fits, with no margin; anything that raises per-commit latency — fixture
bloat locally, a loaded or throttled CI runner, contention from the other lanes
in the same binary, or simply adding another system table — pushes it over. The
flake is latency-amplified, not random, so a green local run on a clean fixture
is not evidence that CI is safe.

The direct measurement is the load-bearing evidence, not the pass rates. Lane
wall time:

| build | fixture | lane wall time |
| --- | --- | --- |
| base | polluted | 42-112s |
| base | clean | 60-86s |
| fix | polluted | 11-18s |
| fix | clean | 6.4-6.9s |

That is the write amplification measured from the outside, it holds at both
fixture states, and on a clean fixture it is a 10x reduction in the lane.

## Cleanup hang seen on the base batch, not the FU10 flake

One base lane was killed by its `timeout 1800` wrapper after 27m25s with only
31s of CPU. `sample` put the test thread in
`drop_provider_databases_for_test` (`reconciliation_tests.rs:1321`), the FU10
test's own MySQL cleanup, with every tokio worker parked in `kevent` — blocked
on the server, not on a lost wakeup, and past every assertion in the test body.

It was draining the pollution the investigation itself had created: the fixture
measured 5 schemas / 0 user tables afterwards, and the next lane was the fastest
of the batch at 42s. So this is an artifact, not a product defect. It is worth
recording anyway that the cleanup has no timeout of its own, so a slow provider
wedges the whole lane indefinitely rather than failing it. Out of scope here.

## Second defect: the fix destabilised a neighbouring test

`projection::work::tests::projection_observer_cancellation_preserves_newer_token`
started failing with `stale_no_op_count` = 3 against an expected 1. This one is
**caused by the fix**, and the attribution is measured, not assumed — the same
isolated batch on both binaries, built from the same tree:

| build | runs | failures |
| --- | --- | --- |
| base | 800 | 0 |
| fix | 600 | 5 |

At 5/600 against 0/800 this is not noise (Fisher exact p≈0.02), and the earlier
reading of it as a pre-existing flake was wrong.

Probes on the publication path settled the mechanism. The sequence of
publications is **identical** in passing and failing runs — same three
publications, same order, same single catch-up drain. Only the classification of
two of them differs:

```
passing:  seq=10 Applied | seq=11 Applied   seq=12 Applied   | seq=11 StaleNoOp  -> 1
failing:  seq=10 Applied | seq=11 StaleNoOp seq=12 StaleNoOp | seq=11 StaleNoOp  -> 3
```

`publish_table_projection_once` returns `StaleNoOp` when the durable
`_projection_fences` row already holds a token greater than or equal to the one
being published (`publication.rs:143-149`). So the classification turns on
whether the cancelled newer-token task had already written its fence row when
the cancellation landed. If it had, the catch-up that replays token 12 is a
no-op and the older token 11 behind it is too.

That is a benign race: both orders converge on the same durable state, which is
why every contract assertion in the failing runs still held — the cancelled
newer token won (`projected_table_source_token == Some(newer)`),
`token_lag_scope_count == 0`, `delayed_retry_count == 1`. Removing 19 no-op
commits from the system tenant simply moved which side of it the test usually
lands on, by letting the newer-token publication reach durability sooner.

The absolute `stale_no_op_count == 1` therefore pinned a scheduling coincidence.
The test now takes a baseline after the cancellation phase and asserts the stale
replay adds **exactly one** — still an exact count, but of the one publication
the phase actually performs, and it also now asserts that the replay leaves the
published token untouched. No assertion was relaxed, and the phase-2 assertions
are unchanged.

Rerun after the change: **600 runs, 0 failures** on the fix build.

## Verification

Worktree `nimbus-fu10-projection`, branch `codex/fu10-projection-flake`, macOS,
debug build, all three external-provider fixtures up.

| gate | result |
| --- | --- |
| `cargo fmt --all --check` | clean |
| `make clippy` | rc=0, no first-party warnings |
| `nimbus-system` lane, 3 runs, all fixtures | 72 passed / 0 failed each, 6.4-6.9s |
| `projection_observer_cancellation_preserves_newer_token`, isolated | 600 runs, 0 failures |
| `engine_skips_the_durable_write_for_an_unchanged_table_schema` | passes |
| `make test` (full workspace) | 2 failures, both pre-existing — see below |

Two notes on running these gates, because both cost time to rediscover:

- A fresh worktree needs `npm install` before `make clippy` or `make check`.
  Without it the gate dies in `nimbus-ui` codegen, well before any Rust runs,
  and the error names npm rather than the missing install.
- `make test` does not export the provider fixture environment. Source it first.
  Otherwise 69 provider tests fail fail-closed by design — they refuse to skip
  silently — and the output looks like a catastrophic regression.

### The two remaining `make test` failures are pre-existing

`tests::ppsc::differential::{redb,sqlite}_ppsc_seeded_journal_differential` both
fail on `pressure.rs:88`, a precondition assert that reads
`publisher_queue_capacity == 1` and gets 32, the default from
`NIMBUS_COMMITTER_PUBLISHER_QUEUE_SIZE` (nothing in the repo sets that variable).

They are not caused by this change. Running the full suite on a base build of
the same tree, with the same fixtures, fails **11** tests: these same two, plus
nine `libsql_replica_provider` tests that the fix run passed. The fix run's
failure set is a strict subset of base's, so this change introduces no new
failure.

The pair interferes with itself rather than with anything else: each passes
alone, and running just the two together reproduces one failure. Worth a
follow-up, but it belongs to whoever owns PPSC, not to FU10.
