# FU12 — BatchWriteItem whole-request rejection rules

Branch `codex/fu12-batch-rules`, base `origin/main @7c0ee550c`.

FU11 established *when* BatchWriteItem validates: the whole request, before any
op runs. FU12 fills in *what* it validates. Two of AWS's documented
whole-request rejection causes had no implementation in Nimbus.

## What AWS actually specifies

From the BatchWriteItem API reference, the list of conditions under which
DynamoDB "rejects the entire batch write operation":

> - One or more tables specified in the `BatchWriteItem` request does not exist.
> - Primary key attributes specified on an item in the request do not match
>   those in the corresponding table's primary key schema.
> - You try to perform multiple operations on the same item in the same
>   `BatchWriteItem` request. For example, you cannot put and delete the same
>   item in the same `BatchWriteItem` request.
> - Your request contains at least two items with identical hash and range keys
>   (which essentially is two put operations).
> - There are more than 25 requests in the batch.
> - Any individual item in a batch exceeds 400 KB.
> - The total request size exceeds 16 MB.

Each row's status in Nimbus before this change:

| Rule | Before FU12 |
| --- | --- |
| Table does not exist | enforced (`load_key_schema` → `ResourceNotFoundException`) |
| Key attributes do not match the key schema | enforced (`primary_key_id`) |
| Multiple operations on the same item | **absent** — applied last-writer-wins |
| Two items with identical hash and range keys | **absent** — same gap, put+put form |
| More than 25 requests | enforced (`MAX_BATCH_WRITE_OPS`) |
| Individual item over 400 KB | **absent** |
| Total request over 16 MB | enforced at the transport (see below) |

The two absent rules are what FU12 implements. The other rows were verified,
not assumed — see "Rules that needed no code" below.

### Units

DynamoDB's service quotas are explicit that these are binary units:

> All size measurements in DynamoDB use binary-based units. DynamoDB denotes
> 1 KB = 1024 bytes, 1 MB = 1024 KB.

So the item ceiling is 409,600 bytes, not 400,000, and the request ceiling is
16,777,216 bytes. `MAX_ITEM_SIZE_BYTES` is written `400 * 1024` with that quote
beside it so nobody "corrects" it to a decimal KB later.

### How an item's size is counted

> The total size of an item is the sum of the lengths of its attribute names and
> values, plus any applicable overhead.

Attribute *names* count, which is why the boundary tests below have to account
for them. `extenddb_core::types::item_size_bytes` implements this, and FU12 uses
it rather than measuring the wire encoding — the JSON an item travels in is a
different and larger number (binary attributes are base64 on the wire), and it
is the request-body limit's business, not this rule's.

### The duplicate-key error text

AWS returns `ValidationException` with the message
`Provided list of item keys contains duplicates`. That exact string is what
Nimbus now returns, so a client matching on the message behaves the same way
against both.

## The change

All of it is in `prepare_batch_writes`, the pass FU11 introduced, so both rules
run before any op executes and a rejection leaves nothing applied.

`crates/nimbus-dynamodb/src/attribute_value.rs` — new `MAX_ITEM_SIZE_BYTES` and
`validate_item_size`, placed next to `validate_item` because this is an
item-level rule, not a batch-level one.

`crates/nimbus-dynamodb/src/commands/batch.rs`:

- The Put arm of `prepare_batch_writes` calls `validate_item_size` alongside the
  existing `validate_item`.
- A new `reject_duplicate_items` pass runs over the prepared ops, keyed on
  `(table name, DocumentId)`. `DocumentId` is derived from the full primary key,
  so hash-only and hash+range tables are both covered by the same check, and a
  put and a delete of one item collide exactly as two puts do.
- Item identity includes the table: the same key under two table names is two
  different items, and the request stays valid. This is pinned by a test rather
  than left to inference.
- `batch_write_item`'s doc comment now names the enforced rules and records why
  the 16 MB ceiling is not among them.

## Rules that needed no code

**The 25-op limit was already enforced.** `MAX_BATCH_WRITE_OPS: usize = 25` in
`batch.rs`, with `batch_write_over_25_ops_is_validation_error` submitting 26 ops.
No change; the existing test covers the requested case.

**A batch-level 16 MB check would be unreachable.** Once no item may exceed
409,600 bytes and no request may carry more than 25 ops, the largest sum of item
sizes a valid request can reach is 25 × 409,600 = 10,240,000 bytes — well under
16,777,216. A sum-based total-request check could never fire, so adding one
would have been dead code that reads like a safeguard.

The 16 MB ceiling is not a sum of item sizes in any case. AWS describes it as a
network-payload bound — a `BatchWriteItem` "can transmit up to 16MB of data over
the network", and "an item's representation might be greater than 400KB while
being sent in DynamoDB's JSON format". It is enforced where the wire bytes
actually exist, in the DynamoDB listener:
`crates/nimbus-server/src/adapters/dynamodb/listener.rs:32`,
`const MAX_REQUEST_BODY_BYTES: usize = 16 * 1024 * 1024;`, applied as
`DefaultBodyLimit::max(MAX_REQUEST_BODY_BYTES)`, with an existing test (F13)
that posts `MAX_REQUEST_BODY_BYTES + 1` bytes. So the rule holds; it is simply
enforced one layer up, and no oversized-request test was added at the command
layer because the command layer never sees the payload.

```

BatchWriteItemOutput { unprocessed_items: {}, ... }
```

The two positive controls passed in the same RED run

failures are the new rules and not a broken fixture.

## Tests added

| Test | Pins |
| --- | --- |
| `batch_write_duplicate_put_keys_is_validation_error` | two puts of one key rejected, message contains `duplicates`, nothing applied |
| `batch_write_put_and_delete_of_same_key_is_validation_error` | put+delete of one key rejected; a pre-existing item survives with its original value, so neither op ran |
| `batch_write_same_key_in_two_tables_is_not_a_duplicate` | the rule is per item, not per key — cross-table request succeeds and both writes land |
| `batch_write_oversized_item_is_validation_error` | item over 400 KiB rejected, and the well-formed op ahead of it is not applied |
| `batch_write_item_just_under_the_size_limit_is_accepted` | the ceiling is inclusive; an item at exactly 400 KiB is accepted |

The last two bracket the boundary precisely. The accepted item is a blob of
`MAX - 9` alongside 9 bytes of other content — names `pk` (2) and `blob` (4)
plus the key's value `big` (3) — landing at exactly 409,600; the rejected one is
a blob of `MAX` with those same 9 bytes on top. That pair confirms three things
at once: attribute names are counted, values are counted, and the comparison is
strictly greater-than. It also confirms `item_size_bytes` adds no per-attribute
overhead beyond names and values, since the accepted item would otherwise have
spilled past the ceiling.

`batch_write_runtime_failure_leaves_earlier_ops_applied` (FU11) still passes
unmodified — the new rules are validation rules and did not turn the batch
atomic.

## One pre-existing test changed

`commands::stream::tests::capture::batch_write_emits_stream_records` built its
request as put `fresh`, put `old`, delete `fresh` — two operations on `fresh`,
which is exactly what AWS rejects. Its purpose is INSERT/MODIFY/REMOVE stream
coverage, not same-item legality, so the fix was to make the request legal
without touching what it asserts: seed a second item `doomed` and delete that
instead. The assertion still names every emitted record and its event type, now
five instead of four. No assertion was weakened.

That the test existed at all is the clearest evidence the gap was real: an
illegal request was routine enough to be written into a test by accident.

## Follow-ups worth a ticket

**The 400 KiB rule is only on the BatchWriteItem path.** `PutItem`,
`UpdateItem`, and `TransactWriteItems` accept an oversized item today. FU12's
brief was BatchWriteItem's whole-request rules, and `validate_item_size` was
deliberately placed in `attribute_value.rs` next to `validate_item` so those
call sites are a one-line addition each — but each needs its own fail-before
test and its own check of what AWS returns (`TransactWriteItems` in particular
reports failures differently), which is a separate change, not a drive-by.

**`extenddb_core`'s item sizing undercounts nested collections.** AWS specifies
that "each `List` or `Map` element also requires 1 byte of overhead", and
`attribute_value_size` in the pinned `extenddb` revision does not add it. The
effect is bounded and small — one byte per element — so it only matters for an
item sitting within a few bytes of the ceiling while holding a large nested
collection, but it means Nimbus will accept a handful of items AWS would reject.
The fix belongs upstream in `extenddb`, which owns `AttributeValue` sizing;
forking the dependency over one byte per element is not worth it.
