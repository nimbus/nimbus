# FU11 — BatchWriteItem validates the whole request before applying any of it

Status: fixed. One file changed, `crates/nimbus-dynamodb/src/commands/batch.rs`.

## The defect

`batch_write_item` interleaved validation and execution: for each op it ran
`validate_item`, `primary_key_id`, and `item_to_fields`, then immediately
committed that op, then moved to the next. A malformed op therefore returned
`ValidationException` **after** every op ahead of it had already been applied.

The code presented that as compliance:

```rust
/// Note: unlike TransactWriteItems this is **not** atomic — a
/// later validation error leaves earlier writes applied (DynamoDB semantics).
```

The parenthetical is false, and a test named
`batch_write_ops_stay_independent_of_each_other` pinned the divergence as
intended behavior — which is what stops the next reader from filing it.

## The contract, from the AWS API reference

[API_BatchWriteItem][ref] draws one line and Nimbus had it in the wrong place.

**Validation rejects the whole request.** "If one or more of the following is
true, DynamoDB rejects the entire batch write operation:" — the list includes
"One or more tables specified in the `BatchWriteItem` request does not exist",
"Primary key attributes specified on an item in the request do not match those
in the corresponding table's primary key schema", "There are more than 25
requests in the batch", and "Any individual item in a batch exceeds 400 KB".
Rejection is of the *operation*, not of the offending op, and none of it is
applied.

**Runtime failure is per-item and reported, not raised.** "The individual
`PutItem` and `DeleteItem` operations specified in `BatchWriteItem` are atomic;
however `BatchWriteItem` as a whole is not. If any requested operations fail
because the table's provisioned throughput is exceeded or an internal
processing failure occurs, the failed operations are returned in the
`UnprocessedItems` response parameter." That is a 200 response whose successful
ops stay applied.

So "not atomic" is true of BatchWriteItem, but it describes the **runtime**
half. Nimbus was applying it to the validation half, where AWS is all-or-nothing.

[ref]: https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_BatchWriteItem.html

## The change

`batch_write_item` is now two passes over the request:

1. `prepare_batch_writes` resolves each table's key schema once and validates
   every op, returning `Vec<PreparedWrite>`. This is where every existing check
   moved unchanged: the exactly-one-of-Put/Delete shape, `validate_item`,
   `primary_key_id` (the key-schema match), `item_to_fields`, plus table
   resolution via `control_plane::load_key_schema` and `TableName::new`.
2. `execute_prepared_write` applies one prepared op in its own single-item
   transaction, exactly as before.

`PreparedWrite` carries the resolved table, `DocumentId`, extracted keys, and —
for a Put — the converted fields, so nothing in the execution pass can fail for
a validation reason. The op count checks (empty, >25) already ran up front and
are unchanged.

Nothing about execution changed. Each op still commits in its own
`execute_single_item_transaction`, which is what keeps ops independent while
reading the prior image inside the transaction that replaces it (FU3), so the
stream-record fidelity that FU3 established is untouched — its two concurrency
tests pass unmodified.

The false comment is replaced by the two halves stated separately, each tied to
what AWS actually does, including why `UnprocessedItems` is always empty here
(the Nimbus store neither throttles nor partially processes a healthy request,
so a genuine runtime failure surfaces as an error instead of as a retryable
item list).

## Tests

`batch_write_ops_stay_independent_of_each_other` pinned the wrong contract, so
it is rewritten rather than kept:

| Test | Pins |
| --- | --- |
| `batch_write_validation_failure_applies_nothing` | A trailing op missing its partition key returns `ValidationException` and the well-formed op ahead of it is **absent** from the store |
| `batch_write_request_with_both_put_and_delete_is_rejected` (extended) | Same guarantee for the malformed-shape path: a valid op now precedes the both-Put-and-Delete op and must not be applied |
| `batch_write_runtime_failure_leaves_earlier_ops_applied` (new) | Per-item independence survives: with a commit fault injected on the second op only, the error is **not** a `ValidationException`, the first op stays applied, and the second applied nothing |

The runtime case is driven by
`inject_error_on_nth_hit(PREPARE_COMPLETE, 2, Error::Internal(..))`. Each op
commits in its own transaction, so the second hit of the commit fault is the
second op: the failure lands mid-batch, after the first op is durable. That is
the closest deterministic stand-in for AWS's internal-processing-failure case,
and it is a `nimbus_core::Error::Internal`, which maps well clear of the
validation taxonomy.

### Fail-before

Both validation tests fail on the unmodified implementation, at the assertion
that names the guarantee:

```
FAIL batch_write_request_with_both_put_and_delete_is_rejected
  panicked at batch.rs:426: the malformed request shape rejects the whole batch,
  including the well-formed op ahead of it
FAIL batch_write_validation_failure_applies_nothing
  panicked at batch.rs:696: a validation error rejects the whole request: the
  well-formed op that preceded it must not have been applied
Summary: 8 tests run: 6 passed, 2 failed
```

`batch_write_runtime_failure_leaves_earlier_ops_applied` passes **before and
after** by design: it guards the behavior the fix had to preserve, so it would
have caught an over-correction into whole-batch atomicity.

## Out of scope, worth a ticket

AWS's whole-request rejection list also covers cases Nimbus does not check at
all, and this change does not add them: "You try to perform multiple operations
on the same item in the same `BatchWriteItem` request" / "at least two items
with identical hash and range keys", and the 400 KB per-item / 16 MB per-request
size limits. Nimbus applies a duplicate-keyed batch as sequential
last-writer-wins instead of rejecting it. That is a distinct divergence from the
one FU11 fixes — a missing rule, not a misordered one — and the validate-first
structure landed here is where such a rule would go: one pass over
`prepare_batch_writes`'s output before execution starts.
