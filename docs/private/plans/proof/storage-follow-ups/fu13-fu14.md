# FU13 + FU14 — the 400 KiB ceiling on every write path, over correct sizing

Branch `codex/fu13-item-sizing`, base `origin/main @4abdc3768`.

FU12 put the 400 KiB item ceiling on `BatchWriteItem` and closed with two
follow-ups. FU13 is the first: `PutItem`, `UpdateItem`, and
`TransactWriteItems` still accepted an oversized item. FU14 is the second: the
sizing function FU12 used undercounts every item holding a nested collection, so
even the one enforced path measured the wrong number.

They ship as one change because they are one change. Putting the ceiling on
three more paths while the ruler is short would have enshrined the wrong number
in four places instead of one.

## What AWS actually specifies

### Item size

From [DynamoDB item sizes and formats][sizes]:

> The total size of an item is the sum of the lengths of its attribute names and
> values, plus any applicable overhead.

and, per attribute type:

> - **String** — the length of the UTF-8 encoded bytes.
> - **Number** — (1 byte per two significant digits) + (1 byte). Leading and
>   trailing zeros are trimmed.
> - **Binary** — the number of bytes in the binary value.
> - **Boolean**, **Null** — 1 byte.
> - **List** or **Map** — (length of the attribute name) + sum (size of nested
>   elements) + (3 bytes). **Each `List` or `Map` element also requires 1 byte
>   of overhead.**
> - **String Set**, **Number Set**, **Binary Set** — the sum of the sizes of the
>   elements.

The emphasized sentence is FU14's whole subject. The 3-byte collection overhead
is charged once per collection; the 1-byte element overhead is charged once per
*element*, at every level of nesting.

Two rules that fall out of the type list and are easy to get wrong, so both are
pinned by tests:

- A number's size is driven by *significant* digits, not characters. `100` is
  1E2 — one significant digit, 2 bytes — while `1002` has four, 3 bytes. Zero is
  1 byte. A negative sign adds 1. With DynamoDB's 38-significant-digit maximum
  the value caps at 21 bytes.
- A set carries no overhead of its own and its elements carry no names. A `Map`
  of the same members is strictly larger than the equivalent set.

[sizes]: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/CapacityUnitCalculations.html

### Units

Unchanged from FU12, restated because the constant moved: DynamoDB's quotas are
binary, `1 KB = 1024 bytes`, so the ceiling is 409,600 bytes. `MAX_ITEM_SIZE_BYTES`
is still written `400 * 1024` with that note beside it.

### The rejection messages

| Path | Shape | Message |
| --- | --- | --- |
| `PutItem`, `BatchWriteItem` | `ValidationException` (HTTP 400) | `Item size has exceeded the maximum allowed size` |
| `UpdateItem` | `ValidationException` (HTTP 400) | `Item size to update has exceeded the maximum allowed size` |
| `TransactWriteItems` | `TransactionCanceledException` (HTTP 400) + per-op `CancellationReason` | code `ValidationError`, message `Item size to update has exceeded the maximum allowed size` |

`UpdateItem` has its own wording because its subject is different: the item the
update *produces*, not the payload. AWS's [TransactWriteItems API
reference][twi] lists `ValidationError` among the cancellation-reason codes with
that same "Item size to update" message, and it is the only size-related message
in that documented set.

[twi]: https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html

### The resulting item, not the request

The `UpdateItem` ceiling applies to the item after the update is applied. This
is not an inference from the message wording alone — it is the only reading
consistent with the operation: an `UpdateItem` request carries a key and an
expression, so its payload is a few hundred bytes even when the stored item it
targets is 399 KiB and the `SET` pushes it over. If the rule measured the
request, it could never fire. `update_measures_the_resulting_item_not_the_request_payload`
pins the converse case too — a request that is itself large is fine as long as
the item it produces is not.

## The change

### FU14 — `crates/nimbus-dynamodb/src/item_size.rs` (new)

Nimbus now owns item sizing. The module holds `item_size_bytes`,
`attribute_value_size`, `exceeds_max_item_size`, the two `validate_*` entry
points, the ceiling, and both AWS messages — the whole concept in one place.

`extenddb-core` is a pinned git dependency, so its `attribute_value_size` could
not be fixed in place. It is also not the right owner: the rule is small, fully
specified by public documentation, and load-bearing for a limit Nimbus enforces.
FU12 speculated the fix belonged upstream; owning ~140 lines of documented
arithmetic is cheaper than carrying a fork or waiting on a release.

The module sits at the crate root beside `attribute_value.rs`, `key.rs`, and
`expression.rs` rather than under `commands/`, because sizing is an item-level
rule that four commands consume, not any one command's concern. That also lets
`attribute_value.rs` go back to being a pure codec: FU12's `MAX_ITEM_SIZE_BYTES`
and `validate_item_size` moved out of it.

### FU13 — the three unenforced paths

`crates/nimbus-dynamodb/src/commands/item.rs`:

- `put_item` calls `validate_item_size` immediately after `validate_item`,
  before any table load or storage work.
- `update_item` calls `validate_updated_item_size(&new_item)` inside the
  transaction plan, after `apply_update` has produced the resulting item and
  before `item_to_fields` serializes it.

`crates/nimbus-dynamodb/src/commands/transact.rs` — the Put and Update arms of
`plan_one` mark an op `failed` when its item exceeds the ceiling, and give it a
`ValidationError` cancellation reason via the new `size_violation_reason`.

`crates/nimbus-dynamodb/src/commands/batch.rs` — migrated to the new sizing
function. The behavior change is FU14's: the path now rejects items it used to
accept.

### FU11's ordering invariant holds without restructuring

FU11 (PR #267, `e3358f27b`) established that a request is validated in full
before any of it is applied. Each new check sits inside an existing pass that
already had that property:

- `put_item` and `update_item` run through `execute_single_item_transaction`,
  where an `Err` from the plan closure rolls the session back and returns. The
  update's check is *inside* the transaction, which is where it has to be — the
  resulting item does not exist until the stored item has been read — but
  nothing commits.
- `transact_write_items` runs `plan_writes` to completion before any commit, and
  cancels if any planned op is `failed`. This is the same pass FU12's
  whole-request rules use.

No new validation phase was introduced, and no existing one moved.

## Judgment calls

Three, each recorded because the brief asked for honesty over a confident guess.

**The transacted-Put error shape is inferred, not confirmed.** A transacted Put
carries its item in the request, so its size is knowable without reading
storage — which means AWS *could* reject it up front with a plain
`ValidationException("Item size has exceeded the maximum allowed size")` the way
`PutItem` does, rather than cancelling the transaction. I could not confirm
either behavior against a live endpoint, and AWS's documentation does not settle
it: the plain "Item size has exceeded…" message does not appear in the
documented `CancellationReason` code set, while `ValidationError` +
"Item size to update has exceeded…" does. Nimbus cancels for both Put and
Update, which keeps one rule for one limit and keeps the per-op position
information a client needs to know *which* of 100 ops was too big. If a
compatibility report shows AWS validating transacted Puts eagerly, the Put arm
is a small change and `transact_write_oversized_put_cancels_with_a_validation_error_reason`
is the test that would flip.

**Condition failure outranks size violation on a single op.** When one op both
fails its condition and is oversized, Nimbus reports the condition failure. The
reasoning is that an op whose condition failed never writes, so its item's size
is moot, and one op should produce one cancellation reason. This precedence is
not verified against AWS — it is pinned by
`transact_write_condition_failure_outranks_the_size_violation_on_one_op` so that
the choice is visible and a future correction is a one-line change with a test
already pointing at it.

**No FU14 integration test on the `UpdateItem` path.** The undercount fixture is
exercised end-to-end on three paths (put, batch, transact); the fourth would
re-test the same shared function through a fourth caller. `UpdateItem`'s own
integration tests cover the ceiling with scalar items, and the sizing rules are
unit-tested directly.

One further note on sourcing: the set-sizing sentence returned by the fetch of
the AWS sizing page was more detailed than the canonical page's own wording and
may be summarizer paraphrase. The load-bearing claims — 3 bytes fixed overhead
per `List`/`Map`, 1 byte per element, sets carrying no overhead of their own —
are consistent with the page text and are what the implementation uses.

### The witness item

`item_undersized_by_nested_elements` is built so the dependency itself proves
the undercount. It carries a `pk`, a padding string, and a 10-element list of
booleans, sized so that `extenddb_core::types::item_size_bytes` returns exactly
409,600 — legal, accepted — while the new function returns 409,610, one byte per
list element. The integration tests assert the `extenddb_core` figure directly
before submitting, so each is a standing statement about what the old sizing
would have let through, not just about what the new one rejects.

## The 4 MB aggregate transaction rule (second commit)

The first commit's leading follow-up, folded in on the same rationale that
folded FU14 into FU13: a missing AWS size rule on a surface this branch already
owns, and a reachable one — 100 ops at 400 KiB is 40 MB, ten times the limit.
Everything below is the second commit; the sections above describe the first and
are unchanged by it.

### The rule

From the [`TransactWriteItems` API reference][twi], under "DynamoDB rejects the
entire `TransactWriteItems` request if any of the following is true":

> The aggregate size of the items in the transaction exceeds 4 MB.

[ServiceQuotas][quotas] gives the same limit and confirms binary units, as with
the 400 KiB item ceiling: 4 MB is 4,194,304 bytes.

### It rejects, it does not cancel

The brief asked whether this is a plain `ValidationException` ahead of
cancellation semantics. It is, and the documentation settles it by omission
rather than by assertion. The rule appears in the API reference's *rejects the
entire request* list. It does not appear in that page's `TransactionCanceledException`
section, which enumerates the circumstances under which "DynamoDB cancels a
`TransactWriteItems` request", nor in the developer guide's
[error-handling list for transactional writes][txnapis]. A rule that AWS files
under "reject" and pointedly leaves out of both "cancel" enumerations is a
whole-request validation.

That reading also agrees with FU11's ordering invariant on its own terms: the
aggregate is computable from the request alone, so there is no reason to read,
plan, or apply anything before checking it. `validate_transaction_size` runs in
`transact_write_items` immediately after the empty/over-100-op guards and before
`begin_transaction_session` — no session is opened, no snapshot is taken, no op
is planned.

### The sizing basis is item sizes, not payload bytes

AWS says "the aggregate size of the *items* in the transaction", which is the
same noun the 400 KiB rule uses, so the natural reading is the same item-size
arithmetic — `item_size.rs`, not a byte count of the serialized request.

The decisive evidence is [`TransactGetItems`][tgi], which carries the identical
sentence: "the aggregate size of the items in the transaction cannot exceed
4 MB". A `TransactGetItems` request contains only keys and projection
expressions; its 4 MB bound is obviously about the items it will *return*, not
about the bytes it arrives as. The same sentence in the same family cannot mean
request-payload bytes on the write side and accounted item sizes on the read
side. Contrast `BatchWriteItem`'s 16 MB, which AWS describes explicitly as a
limit on the request itself — FU12 enforced that one at the transport, correctly.

### What each op contributes

A judgment call, and the one place this implementation knowingly diverges from
AWS. Only `Put` carries its item in the request. `Update`, `Delete`, and
`ConditionCheck` carry a key; the item each of them touches is not known until
the transaction reads it, and reading is exactly what the check must precede.

So each op contributes what the request actually carries: a `Put`'s item in
full, and a key for the other three. That undercounts a transaction of large
updates relative to AWS. The error direction is the safe one — Nimbus may accept
a transaction AWS would reject, but will never reject one AWS would accept.
Closing the gap would mean either sizing after the reads (giving up the
pre-planning position this rule is documented to hold) or a second pass that
reads every target before validating, which is a materially larger design than
the rule warrants. `the_aggregate_counts_a_put_item_in_full_and_other_ops_by_their_key`
pins the accounting so the choice is visible rather than incidental.

### The message wording is ours

The error *code* (`ValidationException`) and *status* (400) are documented. The
literal wire string is not: it appears in no AWS reference page, developer-guide
page, or error-message table found here, and the one re:Post article that might
have quoted it returned HTTP 403 to every fetch attempt.
`TRANSACTION_TOO_LARGE_MESSAGE` is therefore phrased from AWS's own statement of
the condition — "The aggregate size of the items in the transaction exceeded
4 MB" — and marked as ours in the constant's doc comment. Stated plainly because
it matters: a client matching on this string will not be matching AWS's.

## Follow-ups worth a ticket

**The transacted-Put error shape should be confirmed against AWS.** See the
judgment call above. A single compatibility probe against a live endpoint —
one transaction, one oversized Put, record whether the response is
`ValidationException` or `TransactionCanceledException` — settles it.
