Nimbus Storage Adversarial Audit

2026-08-25 · main @ 9c807015a · seven parallel review lanes (Nimbus ground-truth map, post-SIC delta, celld v0.1.0→v0.2.1, object-store exemplars, durability exemplars, Turso + Convex deep dive, web research) followed by a direct-code verification pass. Rev 3: adjudicated across two rounds of second-model adversarial cross-review (Codex gpt-5.6, same commit) — three findings refuted (M4, M6, M13), two downgraded (H2, H5), one reopened by joint agreement (M2), several reframed as owned decisions. Original finding IDs kept stable for traceability. Review only — no code changed.

Verdict: the transactional core is in strong shape — the exposure has moved to the edges. Every exemplar failure class that hits engines at their center (cached-position divergence, waiter starvation, ambiguous commit outcomes, position/state binding) is one Nimbus already closed, in several cases with a better mechanism than the exemplar. The confirmed defects that survive both review passes cluster in three places no active plan owns: the nimbus-s3 wire surface, the unfenced embedded default deployment, and the absent commit-log/MVCC retention story (with erasure codec identity and scrub classification as the leading medium hardening items). The active IMV plan and the proposed BLI plan are aimed at real problems — independent engines hit exactly the failures they predict — but BLI has not been promoted or started, and each has a small number of rider items listed below. "Unowned" throughout means no implementation-plan owner; the active architecture-review control plane owns review-driven triage, and this ledger is input to it.

High findings

Each confirmed by direct code read. After the second-model cross-review, three remain HIGH (H1, H3, and the retention half of H4); H2 and H5 are downgraded to MEDIUM but kept in place under their original IDs.

H1 The nimbus-s3 wire surface has a verified defect cluster and no owning plan HIGH nimbus-s3

Three confirmed defects in crates/nimbus-s3/src/service.rs, one explicit compatibility decision to record, and two separate mediums in convex.rs:

  • ListObjectsV2 silently loses one key per page. The continuation token is set to the first unemitted key (service.rs:329), but the next page's cursor filter skips keys <= token (:321-327), so the token key itself is never returned. Every paginated listing of >max-keys objects is missing objects, with no error. There is no pagination test.
  • DeleteObject ignores the If-Match condition family entirely (:274-290) — unconditional delete, 204. A client's conditional delete is honored as an unconditional one, which is strictly worse than rejecting the header.
  • CompleteMultipartUpload persists the client-supplied CRC64NVME unverified (:626); a later checksum-mode GET replays a value Nimbus never computed.
  • Modern AWS SDK default checksum headers get a 400 (:1031-1054). Deliberately fail-closed and honest, but current SDKs send x-amz-checksum-crc32 by default, so stock clients break. A decision item, not a bug.
  • convex.rs:333-336 mints a fresh ULID per store, so concurrent stores of the same logical file orphan a manifest; :534-546 does an O(n) full-bucket list per operation.

Exemplar mountpoint-s3's mock client is an executable spec for D2-style semantics (preconditions evaluated before existence, 412 over 404); celld's four-probe diagnose is the model for asserting wire semantics against a real target.

Fix shape A small S3-conformance lane (pagination biconditional IsTruncated ⟺ token, conditional-delete, checksum recompute-or-reject) plus one owner plan for the wire surface. The engine-side condition machinery is already correct — these are all adapter-layer translation bugs.

H2 Erasure parity bytes are on-disk format; the recorded rationale doesn't say so MED · downgraded nimbus-blob

Each parity shard's BlobHash is both its storage key and the manifest's ShardRef.shard_hash (erasure/store.rs:606-620), and heal re-encodes and demands byte-exact equality — a mismatch returns beyond repair (heal.rs:297-308). So the exact bytes reed-solomon-simd emits are part of the durable format. But the pin reed-solomon-simd = "=3.1.0" sits bare in nimbus-blob/Cargo.toml:31 (verified — neighboring deps carry rationale comments; the recorded rationale for this pin, in the RFS7 research doc, is supply-chain hygiene, not byte stability). No golden parity vector exists — every test re-encodes with the in-process library, so CI passes identically after any upgrade. A maintainer relaxing the pin for its stated reason converts every future heal of pre-upgrade data into an unrepairable state. Boundary note from cross-review: the exact pin plus the NBLE1 version marker already establish a format boundary — the gap is that the constraint's reason is unrecorded and untested, not that the boundary is absent.

Exemplar celld v0.2 hand-ported the pierrec/lz4 encoder (decoder stays lz4_flex) precisely because "format-compatible ≠ same bytes," tested against upstream output vectors.

Fix shape Two cheap changes: a pin comment stating the real constraint, and a checked-in golden parity vector. A codec-identity field in the erasure manifest is optional — unnecessary if the project commits to the rule that any codec change requires an NBLE2 format bump.

Cross-review Downgraded from HIGH: the exact pin, shard-hash verification, and the NBLE1 boundary mean there is no current-corruption evidence — this is latent-upgrade hardening. One aggravating fact the cross-review adds: upstream guarantees cross-version byte compatibility only for shard sizes divisible by 64, and Nimbus accepts other even final shards, so the hazard is real for exactly those shards. The core hardening remains.

H3 The embedded default deployment has no process fence, and encryption removes the one incidental lock HIGH nimbus-storage / nimbus-engine

requires_committer_lease() is false for Redb and SQLite (persistence/tenant/committer_lease.rs:19-31) — the networked providers get the good in-transaction CAS lease; the default deployment gets nothing. There is no data-directory lock, pid file, or already-running check (bootstrap.rs only does create_dir_all). The plain redb control DB is protected only by redb's own native file lock — and the EncryptedFileBackend is a custom backend that opens with plain OpenOptions and an in-process mutex (encrypted_redb.rs:172,194, verified: no flock anywhere in the file), bypassing redb's lock exactly where encryption-at-rest is enabled. Two processes on one data dir each run their own committer, schema cache, and sequence assignment; divergence surfaces late or not at all. One precedent already in-tree sharpens the gap: LocalPackStore takes an exclusive advisory flock on the blob-store root at open — so the blob plane is fenced while the Engine persistence and control roots created in bootstrap.rs are not. The pattern exists; it stops one directory short.

Exemplar celld deleted its 1,665-line clock-based leaser as unsound and now refuses to run anywhere it cannot fence; its analysis is why "single-process by design" needs a mechanical guard, not a convention. Nimbus's right answer is a data-dir advisory lock (fs2 is already the workspace lock crate), not lease machinery.

H4 Commit-log and MVCC retention are unimplemented — a high launch-readiness gap HIGH nimbus-storage / nimbus-blob

The HIGH classification covers exactly the metadata half, which no plan owns: the commit log is never truncated (no removal path exists outside a corruption-injection test); retention.rs prunes only the MVCC version side-tables, defaults to retain_all, and its only callers are tests — so durable_journal_cursor_floor() is always 0 and the floor-rejection machinery is unreachable in production (the guards themselves are unit-tested — retention.rs:528 pins hard-delete denial under the floor — but nothing wires them into a production retention lifecycle); and PITR cost grows without bound because every restore replays from genesis. BLI is blob-plane only, so commit-log truncation, production MVCC pruning, and PITR growth are routed to no plan.

Adjacent but separately owned: the blob half is already recorded in BLI — BLIF1 covers the unsafe eager release (no refcount under content-addressed dedup: PUT A + PUT B identical bytes, DELETE A breaks GET B), blob GC is a correct mark-and-sweep whose every sweep() call site is a test (BLIF3), and BLI-D2 explicitly accepts remote-leg request orphans as pending-GC work. Its contribution here is urgency evidence only: BLI hasn't started while its highest-stakes defect is live.

Exemplar Convex's retention is the design template when this lane starts: four separate windows, prune cutoff clamped to the dependent structure's confirmed-deleted checkpoint, durable bound conservative / in-memory bound aggressive, and validation per page after each read so long scans crossing the floor fail instead of tearing. celld's deleted-retention consequences (O(lifetime) listings, silent wedges) are the cost of shipping additive-only without the deletion story.

H5 Scrub and heal misclassify transient errors as corruption MED · downgraded nimbus-blob

Verified: any Err from direct verification — including transient I/O — becomes a HashMismatch finding and a quarantine push (scrub.rs:1375-1393; same pattern in scrub/rebuild.rs). Heal's byte-equality check returns beyond repair for any mismatch cause. Downgraded from HIGH per cross-review: quarantine retains the bytes as evidence and a same-byte re-put can restore the record, so this is misclassification and an availability/operator-alarm hazard, not demonstrated permanent loss. The fix is unchanged — classify before concluding (NotFound vs transient I/O vs successful-read-wrong-bytes); only the last is corruption — and it still matters to land before BLI wires quarantine state into GC decisions.

Exemplar rustfs hit exactly this (00519714: heal misclassified transient I/O as corruption) and had to separate error classification from the corruption verdict.

Medium findings and reclassified items

Original IDs kept. After both cross-review rounds the MEDIUM set is M1, M7, M10, and the reopened M2, plus the downgraded H2 and H5 above (six total). M5 is routed to the server security-contract review; M8, M9, and M14 are owned decision or documentation work; M4/M6/M13 are refuted in place below; M11/M12 are design-checklist questions, not defects.

M1 Pre-#303 backups fail restore with a raw serde error MED nimbus-cli / nimbus-storage

MaterializedPosition v2 hard-rejects v1 at deserialize, and the two durable homes of a position — the nimbus backup JSON archive and object-storage bundles — kept BACKUP_FORMAT_VERSION = 1 and POINT_IN_TIME_RESTORE_ARCHIVE_VERSION = 1. Restore of any pre-#303 archive dies on a raw serde error before the friendly format check. Important scope note: the restore already fails safely — no old-format data is ever silently restored wrong. The break itself is correct pre-launch; the defect is purely the diagnostic path. Cross-review refinement, accepted: bumping the container versions alone does not fix the diagnostics, because the nested position deserialization fails before the outer version check runs — the fix is header-first parsing (read and check the container version before decoding any payload), then an operator-legible message naming the digest-codec change.

M2 Negative-zero digest normalization — reopened as an IMV codec decision MED · REOPENED nimbus-storage · IMV1

Both review passes now agree on this disposition (the cross-review conceded the scalar nuance in its second round). Verified mechanics: write_f64 collapses −0.0 to +0.0 (materialized_position.rs:483) and the SpecialDouble::NegativeZero leaf digests identically to a plain 0.0 — asserted by canonical_leaf_normalizes_negative_zero. IMV-D7's normalization rationale ("where logical equality treats both zero spellings as one coordinate") holds for GeoPoint coordinates, but the stored scalar value model round-trips "-0" as a distinct client-observable sentinel — so at the document layer the decision's precondition is debatable, and the v2 digest cannot detect a −0/+0 replica drift that v1 could. Joint recommendation: reopen this inside IMV1 while the codec is still open, decide scalar and GeoPoint treatment separately, and land separate tests for each. Deciding now costs less — the decision still needs implementation and verification — while changing later costs a format break.

M3 A #303 test assertion went vacuous LOW nimbus-server tests

Verified: SnapshotFingerprint serializes position, not digest (nimbus-engine/src/verification.rs:18-29), so both digest assertions in core_http/documents_and_commits/consistency.rs:33-40 compare Null == Null and pass on any input. The engine-side twin was updated; the server-side one was missed. Related: the consistency verification endpoint has report semantics by design (HTTP 200 with mismatches in the body), but carries zero tracing, metrics, or alert integration — report-only is fine, unobserved is not.

M4 PITR export "acknowledgement ceiling" REFUTED nimbus-engine

Refuted by cross-review, and I accept it. Reading the durable journal tail at export time is the correct bound: a committed mutation is valid backup input whether or not its client received the acknowledgement — backing up "beyond acks" is not a defect. celld's epoch seal solves a different problem (multiple restorers agreeing on one cut over an object store) whose preconditions Nimbus doesn't have; I transferred the mechanism without checking them. The one real residual — a zombie writer's garbage becoming exportable on an unfenced embedded deployment — is exactly H3, and the H3 fence closes it. The genesis-replay backup cost observation folds into H4's retention lane. Do not add an epoch seal.

M5 Admin surface auth is conditional, not structural ROUTED · server contract nimbus-server

The gate no-ops when local_server_security() is None (local_server/middleware.rs:117-119, same conditional in two other layers), and admin handlers — tenant create/delete, document insert, diagnostics dumps — carry no independent auth. Every shipped binary installs security and non-loopback binding requires an explicitly rotated token, so this is unreachable via first-party paths today; the exposure is any embedder calling nimbus_server::serve directly. Three handlers already fail closed individually (shutdown, token rotation, UI shell) — generalize that pattern. celld's two-listener split (operator API on a loopback-default socket, never a middleware conditional) is the structural version if the server ever grows one. Scope note from cross-review, accepted: this is a server security-contract item, not a storage finding — route it to the public embedding-contract review, not a storage lane.

M6 External-S3 "false green" REFUTED AS STATED verification

Refuted as stated; I verified the refutation. The owning verifier (scripts/verify-nimbus-s3-object-storage.sh:272-320) already implements exactly the celld pattern I recommended: it treats any target-scoped env var as "operator configured a target" and fails loudly when config is partial or RUN_EXTERNAL_S3=1 is missing, prints visible skips, and the Rust harness prints its live/skipped mode, which the verifier parses — it never claims a skip as live evidence. My finding stopped at the raw test file and never read the framework above it. Residual LOW: no hosted CI job runs the live lane, which is a known operational gap, not a false green.

M7 TenantEventRecord.version is written but never checked MED nimbus-storage

validate_integrity hashes the record's own stored version, so a future-versioned record verifies clean and replays as current — a silent-misreplay path on the durable journal closed by one comparison against TENANT_EVENT_RECORD_VERSION. This is the same class as M11's turso 7e8e6f279 — a version or marker that exists but cannot discriminate — and the two exemplars that hit it did so on the replica-bootstrap and silent-misreplay paths respectively; Nimbus has both surfaces. Related diagnostics gap: all seven blob-plane binary formats encode generation only in the magic string, so version skew reports as Corruption — an operator reaches for restore instead of "wrong binary" (acute for the two formats that cross deployment boundaries: backup bundles and the AEAD envelope). Pre-launch this is a diagnostics fix, not a compatibility layer.

M8 tenant_kv_* is a journal-less write plane with an unstated contract OWNED · NKV contract work nimbus-engine

Verified: Engine::tenant_kv_put/delete/apply_batch call store.kv_* directly — no committer, lease, sequence, or journal entry; redb-only, all other providers return Unsupported (engine/kv.rs). Cross-review reframe, accepted: this is a fact, not a violation — the three-route invariant covers client document mutations, and tenant KV is a separate product plane with its own architecture owner (the NKV plan) and its own backup/PITR story to build. Do not route it through the document committer without a design decision by that owner. What stands: the durability contract is unstated and the plane is invisible to PITR and replication today — document that before nimbus-kv ships on top of it.

M9 EncryptedBlobStore::put_stream is non-idempotent against a content-addressed contract DECISION nimbus-blob

A random salt per call (encrypted.rs:45-52) means a retried streamed put of identical plaintext yields a different stored hash. Cross-review reframe, accepted: this is a deliberate contract split — buffered content uses deterministic content-derived seeding, streamed content uses a random per-object salt — not an accidental defect. The consequences are real (streamed retries defeat dedup and can leave reclaimable orphans for the BLI sweep), but changing the seeding is a crypto-contract decision for its owner, not a patch to make from this audit.

M10 Erasure release lacks crash-atomicity; rollback can unlink a committed replica MED nimbus-blob

Narrowed after cross-review to the provable defect candidate: rollback preimage setup treats every read error as absence (erasure/manifest.rs:204-207), so a transient read failure during setup can later cause removal of a replica that exists — only NotFound should mean absent (the same classification rule as H5). The broader "two-marker release protocol" recommendation is withdrawn as unproven necessity; FoundationDB's pattern stays in the pattern library as a reference if BLI's sweep design wants crash-legible reclamation markers.

M11 Journal replay-range absent-marker ambiguity CHECKLIST nimbus-storage

An audit question, not a finding — both reviews agree Nimbus records the relevant event types and validates contiguous PITR positions today. Turso 7e8e6f279: a commit whose payload was all internal bookkeeping was indistinguishable from pre-portable history, and no fresh replica could ever bootstrap that database again. Keep as a design checklist item for future retention or replication work: a replay-range consumer must always distinguish "no user-visible change" from "a change you cannot replay" — an absent marker must never mean both.

M12 Shared-metadata publication ordering — one lock, not two operations CHECKLIST nimbus-engine

An audit question, not a finding — no Nimbus failure site was identified. Turso df979cf71: a fetch_max-protected watermark plus a separately written cached header let an older finalizing commit overwrite a newer one's metadata — escalating from stale metadata to loss. The checklist rule: audit each spot where the per-tenant watermark bump and any shared metadata publish (position, schema version, summary) are separate operations; span both with one lock. Adjacent: turso 46cd926d3's fix — fold multi-field positions into one struct so the triple can't be observed torn — is worth asserting for every MaterializedPosition handoff.

M13 Schedule-only ambiguity exemption REFUTED nimbus-engine

Refuted; I re-read the code and confirm it. The classification lives inside persist_schedule_only_execution_unit (nimbus-engine/src/tenant/committer_lease.rs:277-340): it validates the lease atomically with the batch, snapshots scheduler pre-state, and on write failure reconciles to Committed / RolledBack / Ambiguous — with ambiguous escalating to durable recovery (crash-and-replay), and an unreadable scheduler state also treated as ambiguous. Refuted or downgraded during verification

Pass-one refutations below; the cross-review refutations (M4 acknowledgement ceiling, M6 false green as stated, M13 schedule-only exemption) stand inline under their original IDs above, each re-verified against the code before acceptance.

  • “libSQL replica refresh gives up silently” — refuted. Refresh errors are logged via warn! with full context and recorded in freshness metrics (libsql.rs:601-610), and the freshness barrier falls back to a synchronous refresh_local_cache()? whose error propagates (:498-515). The claim was later re-raised as HIGH on the theory that the freshness barrier depends on the stopped background loop — but the synchronous fallback is exactly what breaks that dependency: a consumer that needs freshness triggers its own refresh and sees the error. Residual is low: the background reschedule stops until the next trigger re-arms it. One advisory survives the refutation — when replica health monitoring is added, derive staleness from log position and alarm on no-advance, never from the refresh loop's own self-reported health (Convex's stale-cache cluster and Litestream's 0.5.6 silent replication stop are both loops that "looked healthy" by doing nothing).
  • “Commit-log replay must be idempotent and isn't” — downgraded. Nimbus replay is not blind re-application: records are byte-compared against the log and gapless-prefix gated (four contiguity gates). The turso full-page-image concern doesn't transfer directly. The live remnant is M11's marker ambiguity.
  • BLIF7 (backup lock race) stays refuted per the BLI plan — do not re-file.
  • Ambiguous-outcome divergence across mutation paths — closed since the failure CLAUDE.md records: classify_durable_write_error is uniform across all three client routes with the correct evidence rule, and the M13 refutation confirms the schedule-only path classifies one layer down — no residual remains.

Pressure-testing the plans — IMV (active) and BLI (proposed)

Blob-lifecycle-integrity (proposed, all tasks todo)

The plan is validated by independent engines hitting exactly its predicted failures. Turso 70220c982 is the live-root thesis in production form: GC dropped a version whose only physical evidence was a checkpoint, producing a resurrected row and an inconsistent secondary index — quote it into BLI0's fail-before evidence. celld shipped additive-only publication without the deletion story and now carries the consequences BLI is designed to prevent. Its rejection of per-object refcounts matches celld's and restic's independent conclusions. After cross-review, one scope addition and one design constraint:

  • Scrub/heal error classification (H5) is not in scope and should be — quarantine feeding GC decisions makes misclassification a deletion hazard, not just a diagnostics one. (M10's NotFound-vs-transient rule is the same fix.)
  • Design constraint, not a task: reader-lifetime pins are unnecessary today — verified: get_stream fully buffers and verifies before returning a reader (local.rs:817-819), so no read spans a GC decision. The constraint to record in BLI4 is that this stays true: if streaming reads ever become lazy, pins must land in the same change.

Withdrawn after cross-review: adding remote-orphan reclamation to BLI (BLI-D2 accepts request orphans as pending-GC work and synchronous S3 reclamation is an explicit plan non-goal — the remote-leg story is owned, deferred by decision); and the erasure two-marker protocol (already withdrawn under M10).

And the biggest fact: BLI hasn't started, while H4 shows the eager unsafe release path is live today. BLIF1 is the single highest-stakes shipped defect in this audit.

Incremental-materialized-verification (active; IMV1 in progress, #303 merged — ledger one step behind)

IMV is building something its exemplar never had. Convex's only live check is a sampled cache-vs-persistence comparison that panics; there is no checker, no fixup tool, no offline cross-check in the OSS drop — and no PITR at all. Nimbus is ahead of the reference here. Items to fold in while IMV1 is open:

  • M2 (−0.0), now reopened by joint agreement, belongs in the canonical codec now — decide scalar and GeoPoint treatment separately, with separate tests; encoding decisions are unfixable post-hoc (Convex is permanently stuck with Int64-before-Float64 and undefined-before-null).
  • M3's vacuous server test rides the same change.
  • Checklist note — name the exemplar for the opaque position type: Convex's RepeatableTimestamp — a proof-carrying wrapper with an enumerated reason — is the shape MaterializedPosition v2's validated construction already has. The remaining work is coverage, not a new type: raw journal cursors and PITR targets still circulate unwrapped outside the backup-export path (which does supply PointInTimeRestoreTarget::Sequence in production — engine/queries/journal.rs:224). turso's SharedWalBackfillProof (position bound to the materialized file's own identity, validated before trust) is the restore-side counterpart.
  • Checklist note — invalidation keys on data change, not storage events: Convex's T3 outage came from compaction invalidating subscriptions for unchanged data (400× amplification). As IMV adds verification-driven rewrites, canonicalization must never look like a write to the subscription layer.

Where Nimbus is ahead of its exemplars

  • Cached-position divergence — immune by construction. celld's worst defect (a cell permanently unactivatable on every node from a cached position optimization) can't occur: MaterializedPosition is a re-derived content digest, markers commit in the same transaction as the rows they describe, and replay has four independent contiguity gates.
  • Waiter propagation. celld has a live 10-second-timeout-masks-real-error bug; Nimbus's ordered publisher answers every waiter on every exit path — the payoff of the #184 deadlock work.
  • Ambiguous-outcome discipline now matches Convex's crash-and-replay rule uniformly, with a stricter evidence standard (durable head re-read from the provider's authoritative recovery path; cached projections rejected as evidence).
  • Commit-authority conditions. All CAS decided at Nimbus's own commit authority, zero conditional writes against buckets — which is why celld's retry-vs-CAS hazards and the S3 conditional-write capability matrix don't apply. Keep the rule stated that plainly.
  • Content addressing beats the ETag protocol. Manifests name content hashes, so check-then-read is atomic without carrying an ETag through every ranged GET (mountpoint's hardest-won requirement). The concurrent-overwrite exposure is availability-only (a 500, never spliced data); reader pins become relevant only if reads ever move off the current fully buffered get_stream design.
  • The commit protocol survived all six turso WAL bug classes on paper: single-transaction atomicity plus in-transaction markers structurally exclude the file-vs-log disagreement family that cost turso a dozen fixes.

Patterns (cheap, high leverage)

  • Golden vectors for every encoder whose output is addressed or digested — parity shards (H2) first; the #303 dual-graph fixture is the in-repo template.
  • Data-dir advisory lock (H3) via the workspace's existing fs2.
  • redb's CrashBackend — a 165-line deterministic three-image (live / durable / last-header) crash harness with sync-count freeze; extends fault injection to non-SQLite artifacts (blob index, erasure stripes, backup bundles) with no VFS hook and no VM.
  • Fault-injection granularity upgrades: sub-checksum-granularity and padding-region faults (sector-granular injection only ever proves checksums work — the VOPR blind spot); and the fsyncgate case, "fsync fails and the page is marked clean" (no application handled it in the CuttleFS study). Turso's DST — simulators that disable fsync faults, no volatile-cache model — is the cautionary tale that apparatus ≠ coverage.
  • Callback-shaped ordering APIs (Convex log.append(…, apply_writes_callback)): where two operations must stay ordered, make the API shape enforce it.
  • A written read-consistency taxonomy per read path (Jepsen's recurring rqlite finding), including the replica read-your-writes contract.
  • Version-skew ≠ corruption diagnostics (M7) for the formats that cross deployment boundaries.
  • Deterministic-permutation (shuttle-style) tests for any side-cache that drives invalidation — Convex shipped six consecutive stale-read bugs in one cache, all in the cache library's concurrency contract, all found only after adding shuttle.
  • Committer headroom by shrinking the critical section, never by parallelizing the writer — Convex's five-commit 2026-07 burst is the worked example that preserves the single-writer invariant.

Do not adopt — complexity consciously declined

  • Convex's concurrent committer (per-commit storage writes drained via FuturesOrdered) — Nimbus's single-writer + two-stage group commit is simpler and already benchmarked at target throughput.
  • Full FoundationDB-style deterministic simulation — take the two-level BUGGIFY shape and coverage-beacon idea only.
  • rustfs's healing state machine and lock manager; streaming erasure reads (whole-shard content-addressed reads keep Nimbus immune to the decode-quorum lockstep bug class).
  • S3 surface breadth: versioning as a stored dimension, object-lock/retention/legal-hold, lifecycle/storage classes, mountpoint's caching layer.
  • Per-object refcounts — stay rejected (BLI, celld, and restic all independently converged on root-set + grace instead).
  • TTL/wall-clock leases anywhere — celld deleted 1,665 lines of them for cause; Nimbus's DB-clock CAS lease is the right primitive, extended (not replaced) per H3.
  • Read-set coarsening fallbacks — Convex chose fail-the-transaction over widen-the-interval; widening trades bounded memory for unbounded false invalidation.
  • An unfenceable convenience mode — celld deleted local-FS mode entirely; Nimbus's embedded mode is genuinely single-process by design, so the answer is the H3 lock, not mode removal.
  • Cross-review guardrails, all agreed: no PITR epoch seal (M4 refuted); no routing of tenant KV through the document committer (owner decision); no unilateral negative-zero change — M2 is reopened inside IMV1 and decided there; no streaming-encryption seeding change without a crypto-contract decision; no erasure two-marker protocol on this audit's evidence alone; no reader-pin machinery while get_stream stays fully buffered.
