6 · Invariant scoreboard

✓ nimbus-core zero I/O — zero dependencies of any kind on I/O crates; pure types + validation (10.8k lines).
✓ nimbus-runtime zero workspace deps — Cargo.toml verified: deno_*, wasmtime, tokio only. Engine coupling isolated in nimbus-bridge, the sole crate depending on both.
✓ Single mutation path — direct and queued paths both run under lock_mutation_sequence() and end at process_commit; call-site census over all 5 adapters found no side door.
✓ Storage atomicity — doc + index effects + commit-log append in one redb txn (batch.rs:49–133). Amber: two independent txn implementations uphold it → C1.
✓ Bundle integrity — recorded SHA-256 re-hashed before every invocation (runtime/bundle.rs verify_integrity; engine-side verification.rs); path-backed bundles without provenance admitted on filesystem trust, as documented.
· Schema optional — documented contract; not re-verified in this pass.
✓ PDP/PEP split (ARCHITECTURE.md §Egress) — nimbus-egress carries zero transport deps; nimbus-proxy enforces but never re-decides; decision log written before response on every terminal path and cancellation-safe. Amber: append failure is swallowed → C3.

10 · Decision AD2 — workload identity: no new crate yet

Decision: keep the existing ladder; revisit at SI0. Identity is already a deliberate three-layer design, and the layer a crate would own — credential issuance — is entirely deferred to service-identity-provider-auth-plan.md (SI0–SI8, all todo, activation-gated on a concrete provider need).

Opaque routing key. Lives in core on purpose so nimbus-proxy's PEP registry can key on it without depending on sandbox crates — a reachability lint keeps it off the request hot path.

refinement — 2026-07-06 plan-portfolio audit

SI0 is provider-independent and executable today: its largest piece — the stable workload subject projection — already ships (nimbus-tenant/src/identity.rs:171 subject(), :203 spiffe_id() render the SI Identity Contract exactly). 11 · Second pass — what the gap sweep added

Three follow-up readers covered the crates the first pass skipped (nimbus-cli at 62k lines, the small crates, the console) plus seven repo-wide hygiene lenses. Headline: zero TODO/FIXME/HACK markers in production code and disciplined typed errors — the additions are consolidation work, not rot. The full list is in the plan; these are the load-bearing ones.

DS1 · docs

ARCHITECTURE.md's crate table is missing 7 crates (nimbus, -cli, -fs, -kv, -object-storage, -s3, -workloads) and credits nimbus-bin with nimbus-cli's job — while claiming "all workspace members."

GR5 · security

13 independent path-sanitization implementations at capability boundaries (fs, proxy, runtime, egress, cli). Divergent traversal defenses are how traversal bugs slip in — consolidate onto the FsCaps/cap-std choke point.

CO1 · engine

The same background-worker scaffold is hand-rolled three times (subscription delivery, trigger candidates, trigger execution) — identical Mutex+Condvar drain loops and shutdown guards. One generic seam absorbs all three.

GR4 · correctness

The two trigger workers disagree on at-least-once: the candidates worker requeues on store error; the execution worker only warns and drops the invocation.

CO2 · server

Operator-route authorization is triplicated across sessions/services/sandboxes resource-control modules — same authenticate → audit → claim-match flow copy-pasted, plus duplicated scope matchers and four byte-identical audit fns.

CO7 · repo-wide

27 files inline the same epoch-millis boilerplate with divergent error handling, and only one crate has an injectable test clock. A core Clock/now_millis() unlocks deterministic time everywhere.

DE6 · cli

The machine guest-API client hand-parses HTTP/1.1 over a unix socket (~250 lines of bespoke framing) while its sibling client uses reqwest.

DE2 · system

nimbus-system/records.rs is a ~1,400-line flat monolith — ~50 record/delete fns spanning six domains in one file at the decomposition threshold.

top recommendation → now GR1 in the plan

C1 — Collapse the two storage write shapes

The atomicity invariant is the most load-bearing rule in the repo, and today two independent transaction implementations both have to keep it true. Merging point writes into the batch core leaves exactly one implementation to audit — the purest depth win available, with no interface change and no protocol surface at risk. C2 and C3 are the fastest follow-ups: both convert a silent degradation into a loud one.
