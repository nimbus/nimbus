# Gate 41: BJA4L Symbol Isolation Audit And Decision

Date: 2026-05-24

## Purpose

This gate completes the first BJA4L evidence slice after Gate 40 found that
the local macOS static proof does not carry to Linux. The goal is to identify
the actual symbol owners, decide which isolation lane Nimbus should implement
next, and prevent unsafe linker policy from being accepted as proof.

## Source Findings

Rusty V8:

- `BUILD.gn` declares `rusty_v8_enable_simdutf = false`, but V8 itself also
  depends on `//third_party/simdutf` through core V8 targets.
- The Deno fork enables `v8 = { default-features = false, features =
  ["simdutf"] }`.
- Deno's `ext/web/lib.rs` uses `v8::simdutf` for base64 paths, so simply
  disabling the Rusty V8 feature is not a drop-in fix.
- Rusty V8's `src/binding.cc` exports `simdutf__...` wrappers that call
  `simdutf::...`.

Bun/WebKit:

- Bun builds with `-fvisibility=hidden` and uses ELF dynamic-list/version
  script controls for the final Bun binary.
- The static embed manifest links prebuilt WebKit archives directly into the
  Nimbus test binary. Final-binary visibility controls do not prevent duplicate
  strong definitions while static archives are being co-linked.
- The current Linux WebKit/Bun release build is intentionally non-PIC:
  Bun passes `-fno-pic`, and WebKit local-mode configuration sets
  `CMAKE_POSITION_INDEPENDENT_CODE = OFF`. A dynamic adapter therefore cannot
  reuse the current release static objects unchanged; BJA4L2 must either prove
  a PIC-capable dynamic artifact or roll back to static namespacing.
- Bun's `src/simdutf_sys/bun-simdutf.cpp` also exports `simdutf__...`
  wrappers around WebKit's `simdutf::...`.
- The WebKit archive comes from the `oven-sh/WebKit` prebuilt identified by
  `WEBKIT_VERSION = 782504c968e2ae06a511c9e7a4d48318b2a23263`.
- `libJavaScriptCore.a` did not report undefined `simdutf::` references in
  the audit, but Bun's `src/simdutf_sys/bun-simdutf.cpp.o` does reference
  WebKit's `simdutf::` API, and 13 manifest objects/archives reported
  undefined `simdutf::` references. Isolation has to cover the whole Bun
  embedder artifact, not only `libWTF.a`.

## Rejected Paths

`--allow-multiple-definition` and `-z muldefs` are rejected. Gate 40 already
proved that this policy links the test binary and then crashes with `SIGSEGV`.
This is not a harmless duplicate symbol family.

Static archive link order is also rejected as a fix. Link order can choose
which definition wins in some weak/interposition cases, but these are broad
strong definitions across two independently built C++ engines. The losing
engine would be running against the wrong runtime dispatch singletons and
wrapper ABI.

Post-build object rewriting with `objcopy --redefine-sym` is not selected for
the product lane. It might be useful as a diagnostic experiment, but it would
require renaming hundreds of mangled C++ symbols plus C wrapper symbols across
objects and archives. That is brittle across WebKit/V8 updates and weak as an
enterprise source-ownership story.

## Strategy Comparison

| Strategy | Pros | Cons | Decision |
| --- | --- | --- | --- |
| Namespace V8/rusty_v8 `simdutf` | Could preserve one final binary and keep Bun/WebKit closer to upstream. | V8 core targets depend on `//third_party/simdutf`, not only Rusty V8's optional wrapper. A safe rename would need broad V8/Chromium build propagation plus Rust wrapper renames. Deno currently uses `v8::simdutf`. | Not first. Keep as fallback only if the Bun-side path fails. |
| Namespace Bun/WebKit `simdutf` | Preserves one final binary and isolates the optional backend instead of changing the default V8/Deno lane. | Requires Nimbus-owned Bun/WebKit source ownership or prebuilt WebKit releases. WebKit is a large fork surface, and Bun's Rust/C wrapper names must also change. | Viable fallback for a strict single-file product, but heavier than needed for the next proof. |
| In-process dynamic Bun adapter | Keeps the process boundary in-process, exposes only the Nimbus Bun C ABI, and avoids static ODR collision by giving Bun/WebKit a hidden/local dynamic object namespace. This is a common plugin boundary for large native runtimes. | Adds an adjacent runtime artifact unless we later implement packaging/extraction. Current Bun/WebKit release objects are non-PIC, so this path first needs a PIC-capable dynamic artifact proof. | Selected first for BJA4L2 feasibility. Gate 42 rejected the current release-object path, so implementation rolls back to static Bun/WebKit namespace isolation unless Nimbus later chooses to own PIC WebKit/Bun artifacts. |

## Decision

BJA4L2 first attempted the in-process dynamic Bun adapter path:

```text
Nimbus process
  -> BunJscExecutionAdapter
  -> load/link libnimbus_bun_jsc_embedder with RTLD_LOCAL-style semantics
  -> explicit nimbus_bun_embed_* C ABI only
  -> Bun/JSC/WebKit symbols hidden inside the dynamic object
```

That path would keep execution in-process and avoid invasive changes to the
existing Deno/V8/Node lane, but it depends on a PIC-capable Bun/WebKit dynamic
artifact. Gate 42 proved the current release manifest cannot be repurposed as
a shared library: WebKit's bmalloc archive contains non-PIC TLS relocations
that lld rejects for `-shared`.

Therefore BJA4L2 rolls back to the source-owned static namespace path:

```text
Nimbus process
  -> same-binary Bun/JSC static link
  -> Nimbus-owned Bun/WebKit namespace isolation
  -> explicit nimbus_bun_embed_* C ABI
```

This better matches Nimbus' single-binary product preference. The dynamic
adapter remains a future fallback only if Nimbus decides to own PIC WebKit/Bun
artifacts.

The linked gate has also been hardened to reject
`--allow-multiple-definition` and `-z muldefs` before running proof work.
