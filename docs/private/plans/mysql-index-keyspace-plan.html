Outcome

The MySQL storage backend maintains every logical index in one bootstrap-created, order-preserving keyspace table, so a tenant schema applies with any number of indexes, the schema apply commits in the same transaction as its journal record, and no DDL statement runs after tenant bootstrap. Index reads return the same documents in the same order as the redb backend for equality, prefix, range, and composite-range scans.

Progress

Progress appears here when the page loads. The status ledger below is the source of truth.

Architecture

The shared order-preserving tuple encoding in crates/nimbus-storage/src/index/ (already used by redb and by the MySQL index_versions history table) becomes the only index key representation on MySQL. The typed generated columns and the per-index InnoDB keys are removed.

Scope

Owns: the MySQL backend of crates/nimbus-storage: the index_entries keyspace table, its maintenance on the document write path, its rebuild on schema apply, its purge on table lifecycle, and index candidate reads through it; removal of the generated-column and per-index DDL path; the MySQL provider tests and the two architecture notes that describe the MySQL index layout (docs/private/architecture/storage/typed-key-columns.md, persistence-engine-baseline.md).

Does not own: the PostgreSQL backend, which keeps one Postgres index per logical index on documents with transactional DDL and no key cap (owner: architecture-review-2026-07-plan.md if parity is wanted later); the libsql backend, which creates no per-index DDL; the index_versions history table and its missing seed for indexes added after documents exist (finding F3, routed to architecture-review-2026-07-plan.md); the nimbus-ui Phase 4 system schema and the re-run of PR #334 CI after this plan merges (owner: nimbus-ui-rebuild-plan.html, UIR23).

Non-goals: trimming or merging indexes in crates/nimbus-system/src/schema.rs; a physical table per logical table; asynchronous index backfill; a migration for existing MySQL tenant databases (pre-launch, no data to migrate).

Invariants

  1. A document write, its index_entries maintenance, its index_versions history, and its commit_log append commit in one MySQL transaction.
  2. After tenant_init_statements runs at bootstrap, the schema-apply, table-lifecycle, and write paths issue no DDL statement. A schema with any number of indexes applies.
  3. Index reads keep filter_index_documents_with_cancel as the authority for exact predicate evaluation and ordering. SQL only narrows candidates. Results match redb for equality, prefix, range, and composite-range scans.
  4. PostgreSQL and libsql behavior does not change.

Decisions

IDDecisionEvidence and consequenceRe-open when
D1One index_entries table per tenant database: table_id VARCHAR(191), index_id VARCHAR(191), document_id VARCHAR(191), encoded_tuple LONGBLOB, PRIMARY KEY (table_id, index_id, document_id), KEY idx_index_entries_tuple (table_id, index_id, encoded_tuple(768)).Ids are 26-character ULIDs; the declared key bytes (764 + 764 + 768) stay under the InnoDB 3072-byte limit. The prefix key orders the first 768 bytes of the encoded tuple; MySQL re-checks the full column for range predicates. LONGBLOB avoids the row-size limit that a VARBINARY tuple would hit, and matches index_versions.A measured read regression on tuples longer than 768 bytes.
D2Write-path maintenance computes one tuple mutation set per write (close tuple from the previous document, open tuple from the current one) and feeds both index_versions and index_entries.index_version_mutations_for_writes already computes exactly this. Sharing it keeps one schema load per write and one encoding.Never; this is the seam.
D3Schema apply diffs indexes by IndexId: purge entries for removed ids, backfill added ids from the table's documents, rebuild an id whose fields changed. Delete-table and hard-delete purge by table_id.Index identity is stable across schema versions (CST5 proof). The redb backend rebuilds every index of the table on every apply; the diff avoids that cost on MySQL where the backfill is row inserts.An index id can change fields without a new identity.
D4Candidate reads select through index_entries by encoded-tuple range built from the shared bounds primitive, then join documents and table_catalog.range_scan_bounds_for_match_prefix in index/bounds.rs already produces (match_prefix, start_key, end_key) for a match prefix; the SQL keyspace uses the bare encoded exact prefix as that match prefix. The historical planner does the same for index_versions.Never; the encoding contract is shared.
D5Dialect-neutral planning lives in crates/nimbus-storage/src/sql/index_keyspace.rs; MySQL SQL lives in crates/nimbus-storage/src/mysql/index_entries.rs. The bootstrap DDL stays in mysql/backend.rs for this plan.Mirrors sql/index_history.rs. The quality ledger asks to split bootstrap DDL from runtime operations in backend.rs when next extended; this plan removes about 150 lines from it instead of extending it, so the split stays with the ledger row.backend.rs grows past 1,500 lines again.

Rejected designs

  • Trim the Phase 4 system schema under 64 keys. Moves the cap to the next table and leaves runtime DDL and the implicit-commit divergence in place. Re-open: never for this defect.
  • Serve current-state reads from index_versions. It is a history concept keyed by tuple hash, it is not seeded for indexes added after documents exist, and retention prunes it. Re-open: never.
  • One physical MySQL table per logical table. Keeps DDL in the schema-apply path, rewrites the table catalog and every reader, and still caps keys per table at 64. Re-open: only if per-table physical isolation becomes a product requirement.
  • Keep generated columns and add the keyspace only past 64 keys. Two read paths and two failure modes for one concept. Re-open: never.
